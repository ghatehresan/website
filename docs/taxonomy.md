# معماری کاتالوگ و دسته‌بندی — طرح مشروط

**وضعیت:** ما هیچ دستهٔ قطعهٔ خودرو یا Attribute تازه‌ای ایجاد نکرده‌ایم. پیش از پاک‌سازی مالک ده‌ها `product_cat` از نوع `megaelectronic_*` وجود داشت؛ اکنون در [REST عمومی](https://ghatehresan.ir/wp-json/wp/v2/product_cat?per_page=100&_fields=id,slug,name,count&_audit=20260924b) فقط یک دستهٔ خالی با slug `megaelectronic_accessories` دیده می‌شود. مخزن مدیریت ۹ نام دستهٔ seed و صفر محصول واقعی دارد. مبنا: [ممیزی](phase-1-audit.md)، [استراتژی برند در بستهٔ رسمی](https://github.com/ghatehresan/brand-ghatehresan/blob/fe9d144e33ce2416db0b7a1469644a085d637a20/brand-ghatehresan.zip) و [schema مدیریت](https://github.com/ghatehresan/ghatehresan-management-system/blob/75b1a462f0e71cde42967f9aa28cbb603b6b8669/ghatehresan-management-system.zip)؛ هیچ‌یک کاتالوگ فروش واقعی نیستند.

## چهار مفهوم جدا

1. **نوع قطعه = `product_cat`** موجود WooCommerce؛ سلسله‌مراتب حداکثر ۲–۳ سطح فقط در صورت SKUهای واقعی. روغن/فیلتر یک «دستهٔ قطعه» است، نه برند یا خودرو.
2. **سازندهٔ قطعه = `product_brand`** موجود WordPress/Woo؛ `pa_brand` الکترونیکی قدیمی نباید در کنار آن به‌عنوان برند موازی حفظ شود. [brands.md](brands.md).
3. **خودرو = مجموعهٔ سازنده/مدل**؛ fitment محصول به خودرو رابطهٔ چندبه‌چندِ دارای شرایط سال/موتور است، نه هزاران دستهٔ تودرتوی خودرو. [vehicles.md](vehicles.md).
4. **مشخصات قابل فیلتر = Attribute محدود**؛ قیمت/موجودی فیلد بومی Woo هستند. OEM/SKU و شواهد سازگاری نیاز به فیلد جست‌وجویی ساختاریافته دارند، نه الزاماً taxonomy عمومی.

## درخت نامزد بر پایهٔ اسناد، نه محصول منتشرشده

| نامزد سطح ۱ | زیردستهٔ محتمل، تنها با SKU/تقاضای واقعی | منشأ نامزد | وضعیت |
|---|---|---|---|
| فیلترها | روغن، هوا، کابین، سوخت | استراتژی آغازین/seed `فیلتر` | نیازمند فید کالا |
| مصرفی موتور | شمع، وایر، تسمه دینام | استراتژی/seed | نیازمند فید کالا |
| روغن و مایعات | روغن موتور، ضدیخ، مایع ترمز، شیشه‌شور | استراتژی/seed | نیازمند قوانین حمل/اصالت |
| برق و روشنایی سبک | لامپ، فیوز، رله، برف‌پاک‌کن | استراتژی/seed `برقی سبک` | نیازمند فید کالا |
| کابین و جانبی | دستگیره، آفتاب‌گیر، کفپوش | استراتژی/seed | نیازمند فید کالا |
| سیستم ترمز | لنت/دیسک جلو/عقب | استراتژی/seed؛ ایمنی حساس | **فقط با اصالت/سازگاری تأییدشده** |
| جلوبندی / بدنه | بر اساس محصول واقعی | seed مدیریت، خارج از تمرکز آغازین استراتژی | تعویق تا توجیه تجاری |

`سایر`/«دسته‌بندی نشده» مقصد SEO نیست. هیچ ترم محصول/برندِ Bosch/Valeo یا خودروی جدید صرفاً به‌خاطر مثال‌های مسئله نباید ساخته شود. دستهٔ بی‌محصول در ناوبری، لندینگ و sitemap نمایش داده نشود.

## قرارداد دادهٔ محصول برای ورود مرحله‌ای

| فیلد | ذخیرهٔ پیشنهادی | شرط صحت و نمایش |
|---|---|---|
| `external_id`/شناسهٔ پایدار | متادیتای کنترل‌شده یا جدول نگاشت plugin | تنها با مالک/منبع معلوم؛ برای sync آینده |
| `sku` = کد داخلی واحد فروش | `WC_Product::set_sku` | یکتا، immutable پس از انتشار مگر نگاشت/ریدایرکت؛ با Part Number یکی فرض نشود |
| Part Number / OEM | دادهٔ جداگانهٔ نرمال‌شده با نام تولیدکننده و alias | صفرهای آغازین حفظ، `4252.46`/`4252 46` جست‌وجوپذیر؛ فقط بعد از سند معتبر |
| نام | عنوان محصول ووکامرس | «نام قطعه + محل نصب + مدل/موتور در صورت قطعیت + برند»؛ اگر چند خودرو سازگارند عنوان نباید القای انحصار کند |
| Category / Brand | `product_cat` / `product_brand` موجود | گروه و برند تأییدشده؛ برگه و توضیح واقعی |
| vehicle fitment | رابطهٔ مجزا (طرح plugin) | تایید سال/تیپ/موتور به‌ازای هر مدل؛ حالت unknown نمایش یابد |
| regular/sale price, stock | Woo native در فاز اول | قیمت معتبر تومان و زمان بروزرسانی، موجودی انبار ≠ امکان تأمین سفارشی |
| وزن/ابعاد/حمل | Woo native | تنها اندازهٔ واقعی برای محاسبهٔ ارسال و شکست‌پذیری |
| گارانتی/اصالت/کشور/جنس | متای حداقلی معتبر | تا ارائهٔ سند سازنده/تأمین‌کننده «نامشخص»؛ صدها attribute بی‌استفاده نسازید |
| Position / side | Attribute کنترل‌شده در دستهٔ مربوط | جلو/عقب، چپ/راست اگر واقعاً تمایز SKU یا جست‌وجو دارد |

## فیلتر و جست‌وجو

- همگانی: قیمت، وضعیت واقعیِ قابل سفارش، برند قطعهٔ تأییدشده، خودرو/مدلِ منتخب. Category-dependent: `position` برای ترمز/چراغ، روغن/ویسکوزیته فقط در روغن، موتور فقط در قطعات مربوط. سال/تیپ تنها اگر ماتریس fitment معتبر و شمار SKU کافی است. فیلتر «اصل/غیراصل» بدون مستندات SKU ایجاد نشود.
- normalize ورودی: `ي/ی`، `ك/ک`، ارقام فارسی/عربی، نیم‌فاصله/فاصله و case انگلیسی؛ **شمارهٔ فنی اصلی و صفرهای آغازین را تغییر ندهید**. وزن جست‌وجو: تطابق دقیق SKU/OEM/شماره فنی بالاتر از نام/برند، سپس سازگاری خودرو. آزمون روی نمونهٔ واقعی و precision/recall قبل از افزودن Elasticsearch/OpenSearch/Meilisearch؛ حجم ۱۸ محصول demo در بررسی اولیه (اکنون صفر محصول عمومی) دلیل ارتقا نیست.
- URL فیلتر/مرتب‌سازی: پیش‌فرض canonical به archive اصلی و noindex طبق [seo.md](seo.md)، نه ساخت صدها لندینگ ترکیبی. فقط لندینگ‌های دستی و دارای متن/محصول کافی.

## Gate ورود/انتشار

1. فایل CSV/Excel/API واقعی با SKU، قیمت تومان، موجودی/lead time، دسته/برند/fitment و **منبع** دریافت و نسخه‌گذاری شود؛ ردیف‌های sample اکسل و `demo.php` ممنوع.
2. dry-run: encoding، ترم‌ها، شناسه/تکرار، نام تجاری، نگاشت واحد پول، حدود قیمت، تصاویر/حق استفاده و تاریخ بازبینی fitment. خطاها به «نیازمند بررسی» quarantine؛ importer هم create و هم update با preview و گزارشِ ردیف دارد.
3. نگاشت `old product_cat ID/URL → disposition` پیش از دست‌کاری demo؛ تغییر slug تنها پس از [طرح ریدایرکت](redirect-plan.md). هیچ کالای واقعاً فروخته‌شده یا سفارش تاریخی را blind delete نکنید.
4. تأیید مسئول کالا/تأمین و مالی، سپس انتشار محدود و تست جست‌وجوی فارسی/لاتین/OEM، variant و سفارش sandbox؛ وظیفهٔ بروزرسانی قیمت/تأمین با فرد مشخص ثبت شود.
